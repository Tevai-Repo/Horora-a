# Horora'a — Spécification v0

> Ce que c'est : pour qui, avec quels mots, dans quelles limites le produit existe. Lu par : l'étude, les développeurs, la QA, le pilote. Écrit par : l'intégrateur, après la porte-engagement. Change par : un changement archivé après le test du pilote. Statut : vide, installée le 2026-10-29 ; sections 1, 2, 4 et 7 à écrire par le pilote, à la main, avant tout besoin. Le comportement du produit vit dans `openspec/specs/`, une capacité par dossier ; ce fichier dit le reste : la vision, les mots, les principes, l'index des capacités, les budgets, les invariants, le hors périmètre. La spec suffit : n'importe quel agent, dans n'importe quel langage, sans une ligne du code d'avant, refait le logiciel en entier ; pas le même code, pas le même écran, pas le même octet, le même usage pour l'utilisateur (decision-fabrication-8, decision-fabrication-20). Les bibliothèques tierces et les données ne sont pas le code source : la spec dit ce qu'elle attend des unes et le schéma des autres. Elle gagne contre le code : un écart est un défaut du code ou une décision qui change la spec. Toute fonctionnalité hors de ce document et des specs est hors périmètre tant qu'une décision ne l'y ajoute pas. Sur un projet existant, l'index des capacités se remplit en premier, relevé depuis les écrans et jamais depuis le code, et chaque capacité reçoit sa spec le jour où un changement la touche (decision-fabrication-12).

## 4. Les capacités

| Capacité | Spec | Ce qu'elle couvre | Couverture |
|---|---|---|---|

Une capacité **couverte** obéit à « la spec gagne contre le code ». Une capacité **non couverte** n'a pas de spec : le code fait foi, faute de mieux, jusqu'au premier changement qui la touche (regle-couverture, decision-fabrication-12). Sur un projet neuf, la colonne ne contient que des capacités couvertes.
